# BOLOLO Smart Control

[![Version](https://img.shields.io/badge/version-0.1.1-2f6f4e.svg)](custom_components/bololo/manifest.json)
[![Release workflow](https://github.com/maycode0-0/bololo-smart-control/actions/workflows/hacs-release.yml/badge.svg)](https://github.com/maycode0-0/bololo-smart-control/actions/workflows/hacs-release.yml)

BOLOLO Smart Control 是面向 Home Assistant 的波咯咯自定义集成。它将云端账号、
设备清单和局域网通信放在同一条设备、状态与控制链路中，默认优先使用 LAN，
无法通过本地通道处理的请求按回退规则交给云端。

## v0.1.1

本版以 **LAN 优先、云端回退** 为默认传输策略，并提供仅云端、仅 LAN 两种模式。
设备实体保持在同一个集成下，切换通道无需建立另一组设备。

重点适配刘海妹妹全能 Z60 系列消毒柜与智能泡奶机 P30。设备字段和控制约束来自
波咯咯 Android App 2.1.86 及其绑定的官方设备页面；静态协议分析、离线测试和真机
验证分别记录。当前尚未完成这两款设备的真机联调，具体固件的 LAN 能力仍需验证。
具体变更见 [v0.1.1 发布说明](docs/releases/0.1.1.md)。

## 通道策略

| 模式 | 读取状态 | 发送控制 |
| --- | --- | --- |
| LAN 优先、云端回退（默认） | 优先读取 LAN，失败时读取云端 | 优先 LAN；只有确认物理命令尚未发送时才允许云端回退 |
| 仅云端 | 云端状态接口 | 云端控制接口 |
| 仅 LAN | 本地连接 | 本地连接；失败直接返回，不调用云端控制 |

```text
设备请求
  |
  +-- 仅云端 ------------------------------------> 云端 HTTPS
  |
  +-- 仅 LAN ------------------------------------> LAN
  |      +-- 本地不可用 --------------------------> 返回失败
  |
  +-- LAN 优先、云端回退 ------------------------> LAN
         +-- 本地读取失败 -----------------------> 云端读取
         +-- 控制尚未发出，本地不可用 -----------> 云端控制
         +-- 控制已发出，结果无法确认 -----------> 返回结果不明，不重复发送
```

“LAN 优先”不代表把一次操作同时发送给设备和云端。尤其是煮沸、消毒等物理动作，
本地发送后若响应超时，集成不会再通过云端重发同一动作。应先确认设备状态，再决定
是否重新操作。

首次配置仍需登录云端账号，取得已绑定设备清单。集成将最小设备库存保存在
Home Assistant 的私有 Store 中。已有缓存后，默认模式启动不强制等待云端登录；
仅 LAN 模式不调用云端，可以使用保存的库存离线重启。仅云端模式启动仍会登录云端。

默认模式会定期更新云端清单，云服务暂时不可达时保留已有清单，继续尝试本地通信。
这不等同于脱离账号独立发现并接管任意设备；新增设备仍应先在 App 绑定，并同步到
本集成的清单中。仅 LAN 模式不刷新云端清单，新增或解绑设备后应先通过云端同步。

本地认证优先使用设备自身返回的 LAN passcode；无需通过云端取得该密码。也可在
配置菜单中为单台设备指定 passcode。能否在具体设备上完成发现和认证，仍取决于
实际固件及网络环境。

## 安装

### HACS 自定义仓库

在 HACS 的“自定义存储库”中添加 `https://github.com/maycode0-0/bololo-smart-control`，
类别选择 **Integration**，搜索 **BOLOLO Smart Control** 并下载安装，然后重启 HA。
首次 Release 需在 GitHub Actions 检查通过后生成；最新安装包见 [Releases](https://github.com/maycode0-0/bololo-smart-control/releases)。

### 安装包

1. 将 `dist/bololo-0.1.1.zip` 解压到 Home Assistant 配置目录。
2. 确认最终文件路径如下，然后重启 Home Assistant：

```text
<ha-config>/custom_components/bololo/manifest.json
```

3. 进入“设置 → 设备与服务 → 添加集成”，搜索 **BOLOLO 波咯咯**。

也可以手动复制本项目的 `custom_components/bololo` 目录。无需配置 YAML，无需另行
安装 Python 运行依赖。Release 中的 `bololo-smart-control.zip` 是 HACS 布局，手动使用
时应解压到 `<ha-config>/custom_components/bololo/`；两种 ZIP 不要解压到同一个层级。

### 已安装版本升级

整体替换 `<ha-config>/custom_components/bololo` 后重启，避免残留旧模块。无需为同一
账号删除并重新添加集成。升级前可备份原组件目录，以便回退。

## 首次配置

1. 在波咯咯 App 中完成设备 Wi-Fi 配网，并将设备绑定到自己的账号。
2. 在 Home Assistant 添加集成，填写 App 使用的手机号或邮箱、密码。中国大陆国家
   区号填写 `86`；仅短信登录的账号应先在 App 设置密码。
3. 使用默认的“LAN 优先、云端回退”模式。需要调整时，在集成的“配置”菜单中
   选择仅云端或仅 LAN。
4. 确保 Home Assistant 能访问设备所在网络。局域网发现通常需要同一广播域；跨
   VLAN、访客网络、无线客户端隔离与防火墙都可能影响发现或直连。
5. 配置完成后，受支持的 Wi-Fi 设备会创建开关、数值、选项与传感器实体。

### 配置菜单

| 配置项 | 用途 |
| --- | --- |
| 传输模式 | 选择 LAN 优先、云端回退（`auto`）、仅云端（`cloud`）或仅 LAN（`lan`） |
| 可选设备 | 选择需要手动覆盖 LAN 参数的设备；无需手动设置时保留自动发现 |
| IPv4 地址 | 为选中设备提供单播发现目标；留空清除该设备的地址覆盖 |
| LAN passcode | 可选的本地认证密码；留空清除该设备的密码覆盖，恢复自动取得 |

保存选项后会重新加载集成，使通道和设备参数生效。修改模式不会更换实体唯一 ID。

### 网络要求

云端服务为 `app.bololoapp3.com`，使用 HTTPS。局域网通道使用以下端口：

| 协议与端口 | 用途 |
| --- | --- |
| UDP `12414` | 向设备发送广播或单播发现请求 |
| UDP `2415` | Home Assistant 接收设备发现报告 |
| TCP `12416` | 与设备建立本地连接、认证、读取和控制 |

**手动填写 IPv4 也需要 UDP 发现可达。** 集成会验证发现公告中的产品键和 MAC
是否与账号清单中的目标设备一致，再建立 TCP 连接；手动地址不会跳过这一步。

本地采用短连接，每次操作结束后关闭连接。端口与认证路径来自原生 SDK 的静态
恢复结果，具体设备是否响应这些服务仍需实机确认。

## 支持范围

当前实体平台包括 `switch`、`number`、`select`、`sensor` 和 `binary_sensor`。

| 型号 | 主要能力 | 验证范围 |
| --- | --- | --- |
| 刘海妹妹全能 Z60 系列消毒柜 | 总开关、自动/烘干/杀菌、保管、等离子、夜间模式、烘干温度、模式时长、工作状态与剩余时间 | 已核对产品定义和官方控制模板；真机待验证 |
| 智能泡奶机 P30 | 总开关、煮沸、静音、常温、目标/当前温度、水源选择、出水量设置、工作状态、故障与出水状态 | 已核对产品定义和官方控制模板；真机待验证 |
| 其他包内 Wi-Fi 产品 | 按产品定义生成标量实体 | 有产品定义，尚未完成同等程度的控制模板核对 |

Z60 的模式切换使用组合命令；P30 的温度设定为 37–95°C，出水量设定为 30–500mL、
步长 5mL。具体范围、产品键和限制见 [设备支持范围](docs/DEVICE_SUPPORT.md)。

P30 的出水状态是只读传感器，当前不提供日常远程出水，也不会自行解除童锁。
APK 中的 7 款 BLE 吸奶器与 1 款传输方式未知的产品不在本次接入范围。

## 状态与控制

默认每 30 秒刷新设备状态。LAN 读取成功时使用本地回读；云端回退读取的是云服务
保存的最近状态。成功读取云端缓存不能证明设备此刻在线，实体属性
`cloud_status_time` 保留服务器提供的状态上报时间，另有默认关闭的“上次状态上报”
诊断实体。

控制后重新读取状态，不使用未经设备确认的数值覆盖显示。云端处理和设备上报可能
造成延迟；查询失败时保留的旧数值不能当作新的设备确认。

业务实体的属性提供以下通信信息：

| 属性 | 含义 |
| --- | --- |
| `connection_mode` | 配置的传输模式：`auto`、`cloud` 或 `lan` |
| `active_transport` | 最近成功通信使用的 `lan` 或 `cloud` 通道 |
| `cloud_status_time` | 云端来源的状态上报时间；本地读取时为空 |

`active_transport` 在成功读取或控制后更新，随后刷新仍以实际成功读取的通道为准。
该属性不是实时在线标记，也不代表物理动作已完成；读取失败时仍可能保留上次通道。
诊断导出包含模式、库存刷新错误类型和逐设备读取结果、最近通道与错误类型，不包含
密码、passcode、IP 或 MAC。

预留、废弃与二进制流程字段不创建普通控制实体。校准、内部编码和自定义场景槽等
实体默认关闭；没有可核实含义的数字不会被伪造成模式选项。当前不复刻完整的配网、
固件升级、奶瓶管理与保养校准向导。

## 故障定位

| 现象 | 优先检查 |
| --- | --- |
| 账号无法登录 | App 账号密码是否有效，国家区号是否为实际注册区号，云端 HTTPS 是否可达 |
| 登录后没有设备 | 设备是否绑定在此账号；当前只接入有定义的 Wi-Fi 产品 |
| 一直使用云端 | 所选模式、设备固件的 LAN 能力、网络隔离及本地认证结果 |
| 局域网发现不到设备 | 自动广播发现是否在同一广播域；手动 IP 则检查路由、UDP `12414`/`2415` 和客户端隔离 |
| 填写了手动 IP 仍无法直连 | 手动 IP 只提供单播发现目标，仍需收到匹配的发现公告；检查 UDP 回包和 TCP `12416` |
| 仅 LAN 模式下不可用 | 该设备是否提供本地服务，以及地址、端口和认证是否正确；该模式不走云端控制 |
| 仅 LAN 模式没有新增设备 | 该模式不访问云端清单；先在 App 绑定，再切换到可访问云端的模式同步 |
| 操作超时后没有自动云重试 | 命令可能已发到设备；为避免重复执行，集成不会跨通道重发结果不明的控制 |
| 状态更新较慢 | 当前是否使用云端缓存，设备是否已产生新的状态上报 |
| P30 没有一键出水 | 当前未实现日常远程出水；校准出水命令不等同于普通出水命令 |
| 更新后仍显示旧名称或旧功能 | 确认完整替换组件目录并重启 HA，检查实际加载的组件版本 |

反馈问题时请附 Home Assistant 版本、集成版本、公开型号、所选模式、相关日志和
复现步骤。诊断与日志应先检查并脱敏，不要附账号、密码、令牌和设备私有地址。

## 开发与验证

使用 Python 3.12 环境安装 `requirements-dev.txt` 后运行：

```sh
python -X utf8 -m pytest -q -p no:cacheprovider
ruff check custom_components tools tests
ruff format --check custom_components tools tests
python tools/build_release.py
```

基础兼容性验证使用真实 Home Assistant 2024.12.5 API，包含集成加载、五个平台注册、
控制服务调用和卸载。离线测试不替代具体设备、固件与实际网络环境下的验证。

本次 v0.1.1 验证共 **128 项测试通过**，Ruff 检查与格式检查通过；LAN 测试包含真实
回环 UDP/TCP 模拟设备、固定协议字节、认证失败和命令超时后禁止重放。

协议元数据可以从指定 APK 重新提取，不执行包内代码：

```sh
python tools/extract_apk.py com.gizwits.MainApplication.apk.1 --summary analysis/product-summary.json
python tools/extract_lan_profiles.py com.gizwits.MainApplication.apk.1
```

官方页面约束独立保存在 `model_overrides.py`；重新提取元数据不会覆盖它们。

推送 `main` 后，GitHub Actions 会在测试、HACS 和 hassfest 全部通过后生成普通
Release。标签和安装包不会被新提交覆盖；后续发版需递增版本，详见 [发版流程](docs/RELEASING.md)。
